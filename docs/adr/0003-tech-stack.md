# 0003. 技術スタック

- 状態: 承認
- 日付: 2026-10-14

## 背景

- 業務では、フロントに Next.js、バックエンドに Go を使っている。業務との近さを重視したい（学んだことを業務に返せる。慣れているので速い）
- フロントとバックエンドの言語が違うと、報酬制度でそれぞれ別に数えられる（2-A-1）
- AI の CLI から、API キーで操作できる必要がある
- 使える時間は約42時間で、見積もりはすでに超えている。時間のかかる選択は避けたい

## 選択肢

### フロント

#### A. Next.js（App Router）＋BFF

画面のデータの取得と更新を Next.js のサーバー経由で行い、Next.js から Go を呼ぶ。認証（Better Auth）も Next.js で動かす。

- 良い点: Better Auth で認証が早く片付く。ブラウザには Cookie だけを持たせ、トークンを渡さない。Go を外に公開しなくてよい。Server Components の素直な使い方になる。業務に近い
- 悪い点: 1回の操作で Lambda を2つ通る。非同期の Server Components は単体テストしにくい（Next.js 公式も E2E テストを勧めている）。App Router は覚えることが多い

#### B. React＋TanStack（Router / Query）の静的 SPA

S3 と CloudFront から配信し、ブラウザから Go を直接呼ぶ。

- 良い点: 構成が単純で、Lambda が1つで済む。コンポーネントの単体テストを書きやすい。表示が速い
- 悪い点: Better Auth は JavaScript のサーバーで動くので、認証の置き場所が別に要る。Go で自前に組むと約3〜5時間増え、CSRF 対策も自分で書く。外部の IdP を使うとローカル実行が難しくなり、ブラウザがトークンを持つ。業務から遠い

#### C. TanStack Start

- 悪い点: サーバーが要るので構成は A とほぼ同じになり、業務からも遠い

### Go の HTTP

#### A. 標準の net/http

- 良い点: Go 1.22 から、メソッドとパスの変数を使ったルーティング（`GET /entries/{id}`）が標準で書ける。標準の型なので、他のライブラリとそのまま組み合わせられる
- 悪い点: ミドルウェアなどを自分で組む部分がある

#### B. Gin（Echo や Chi も同じ位置づけ）

- 良い点: 情報が多い。ミドルウェアが揃っている
- 悪い点: 独自の型（`gin.Context`）を使うので、標準のミドルウェアを使うには変換が要る。入力の検証は OpenAPI から生成したコードで行うので、Gin の機能の出番が少ない

### API の型の共有

#### A. OpenAPI を唯一の正として、両側のコードを生成する

- 良い点: Go と TypeScript で型がずれない。CI で生成し直して、差分がないことを確かめられる
- 悪い点: 仕様を先に書く手間がある

#### B. それぞれ手で型を書く

- 悪い点: 型がずれても気づけない

### DB

PostgreSQL を使う。定番で情報が多く、Better Auth が対応している。本番の候補（Aurora DSQL、Neon）も PostgreSQL 互換（0005）。

## 決定

- フロント: A（Next.js＋BFF）。決め手は、時間内に終えるという目的に対して、認証が一番早く片付くこと
- バックエンド: Go（標準の net/http）
- CLI: Go
- API の契約: OpenAPI。Go は oapi-codegen、TypeScript は openapi-typescript で生成する
- DB: PostgreSQL。Go からは pgx＋sqlc で使い、マイグレーションは goose で行う
- テストの網羅率: gobco で分岐の網羅率（C1）を測る。Go 標準のカバレッジは命令の網羅率（C0）しか測れないため

## 結果

### 良くなること

- 業務と同じ組み合わせなので、学んだことをそのまま業務に返せる
- ブラウザにトークンを持たせない

### 悪くなること・リスク

- Lambda が2つになり、コールドスタートが最大2回起こる。この規模なら許容する
- Next.js の単体テストが書きにくい。画面のロジックは純粋な関数やクライアントコンポーネントに寄せてテストする。テストの中心は Go のテーブル駆動テストにする
