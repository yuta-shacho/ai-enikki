# 0001. ADR で設計の判断を残す

- 状態: 承認
- 日付: 2026-10-14

## 背景

このアプリは、エンジニア報酬制度の評価項目を満たすための学習用です。評価では「いくつかの方法を挙げ、メリット・デメリット・トレードオフを評価したうえで設計したか」が見られます（1-B-2）。

判断の結果だけでなく、比べた選択肢と理由を、後から読める形で残す必要があります。

## 選択肢

### A. ADR（Architecture Decision Records）

- 良い点: 判断ごとに1ファイルなので、何をいつ、なぜ決めたかを追いやすい。コードと同じリポジトリで管理でき、PR でレビューできる
- 悪い点: 書く手間がかかる

### B. 設計書を1つの文書にまとめる

- 良い点: 全体を一度に読める
- 悪い点: 書き換えると、前の判断と理由が消える

### C. PR や Issue の説明に残す

- 良い点: 追加の手間がない
- 悪い点: 散らばって探しにくい。GitHub の外に持ち出しにくい

## 決定

A の ADR を使う。

- 置き場所は `docs/adr/`。ファイル名は `連番-英語の短い名前.md`
- 書き方は [template.md](template.md) に従う。「選択肢」には、選ばなかった案も良い点・悪い点と一緒に書く
- 状態は「下書き → 提案 → 承認」と進む。判断を変えるときは古い ADR を書き換えず、新しい ADR を作って古い方を「置き換え」にする
- 一覧は [README.md](README.md) で管理する

## 結果

### 良くなること

- 1-B-2 の評価の材料がそのまま残る
- 後で判断を見直すとき、当時の前提を確かめられる

### 悪くなること・リスク

- 書く手間が増える。小さな判断は ADR にせず、PR の説明に残す
